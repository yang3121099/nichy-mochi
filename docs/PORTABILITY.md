# 换机与多卡 🍡

一个 Mochi 服务管理一个接头点，以及当前 Linux 环境分配给它的一组 NVIDIA GPU。卡数和 UUID 不写死；空闲负载按卡独立运行、独立调节，真实任务则获得整组优先权。

## 日常命令不变

项目放在 `/users/nichy/code/start/nichy-mochi`，GPU 启动指令仍是：

```bash
cd /users/nichy/code/start && bash nichy-mochi/start.sh /users/nichy/code/start
```

`command.sh` 使用当前可见的全部 GPU：

```bash
cd /users/nichy/code && torchrun --standalone --nnodes=1 --nproc-per-node=gpu main.py
```

`gpu` 为每张可见 GPU 启动一个进程，避免从 8 卡换到 2 卡后仍启动 8 个进程；`--standalone` 为单机任务设置独立 rendezvous。训练代码仍需支持 DDP、按 `LOCAL_RANK` 选择设备，并适配卡数变化带来的全局 batch size 等参数。[PyTorch 官方说明](https://docs.pytorch.org/docs/2.14/elastic/run.html)

GPU 环境需要 Linux、Python 3.9+、bash、可用的 CUDA 版 PyTorch 和 `nvidia-smi`。Mochi 不安装驱动或修改平台分配。空闲负载不使用 NCCL，也不要求 NVLink；业务训练的通信和硬件兼容性由其依赖环境决定。

## 覆盖的部署形式

| 场景 | 行为与条件 |
| --- | --- |
| 更换 GPU 型号、数量或宿主机 | 新服务从当前 CUDA 环境重新识别设备，不复用日志里的旧 UUID |
| 单机 1 / 2 / 4 / 8 卡 | 每张可见卡一个空闲进程；逐卡反馈调节，无固定 8 卡假设 |
| 平台只分配部分卡，如 `CUDA_VISIBLE_DEVICES=7,2` | 以 CUDA 实际返回的 UUID 和顺序为准，只创建这两张卡的负载 |
| 宿主机还有未分配的卡，指标返回 `N/A` | 忽略未分配卡的指标；已分配卡的未知指标仍阻止空闲负载 |
| 型号、速度或利用率不同 | 每张卡独立调节，不用整机平均值掩盖某一张卡；不能保证任意硬件均达目标 |
| 多台 GPU 机器各自处理独立任务 | 每台一个独立接头点和服务；CPU 端上传到对应机器 |
| 两个服务指向同一个共享接头点 | 第二个被目录锁拒绝，即使旧锁来自另一台机器且已过期，也不会自动抢占 |

CUDA 可见设备会重新编号，GPU 数字索引不能当作跨机器身份；UUID 可以避免编号顺序变化带来的错误映射。[NVIDIA 设备选择说明](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)

平台应在启动服务前完成设备隔离；未设置 `CUDA_VISIBLE_DEVICES` 时，CUDA 可见的全部设备都视为本服务可用范围。不要让两个独立服务管理重叠的 GPU。变更分配后应停止旧服务并在新环境重新启动，不在运行中热切换设备。

## 多卡一致让行

任一可见卡存在外部计算进程、显存压力、指标缺失，或任一空闲子进程失败，都停止整组空闲负载。只有整组满足条件才恢复。这样真实多卡任务准备各张卡时，不会与剩余卡上的空闲负载竞争。

收到 Mochi 任务后，不再依赖 GPU 采样判断它是否忙：真实任务整个进程生命周期都受保护，包括 CPU 准备与保存阶段。空闲子进程先 TERM，必要时 KILL，监督进程确认清理完成后才启动任务。GPU 工具报告的宿主机 PID 只用于识别资源变化；实际终止的是本服务创建的进程，不按 GPU PID 列表杀任务。

## 换机和共享文件

新机器采用新的接头点时，上传项目与业务文件，启动后再提交 `command.sh`；不要把旧 `.nichy` 的运行锁、状态文件当作安装文件复制过去。配置和需要的历史备份可单独保留。

若继续使用同一份共享接头点，先正常停止旧机器服务，确认原作业结束后，再启动新机器服务。异常停机留下的锁需要按 [故障恢复](ADMIN.md#故障恢复) 核对；不会自动重跑未确认的任务，也不会在旧机器可能仍运行时接管。

CPU 上传文件与 GPU 本地读取可以使用不同路径。只有选择 POSIX 共享文件系统时，两端才必须访问同一份数据；命令中的工作路径还必须在 GPU 上存在。本机各自的 `.nichy` 不会自动同步。NFS 的一致性、掉线和挂载失效仍需在实际环境验证。

## 明确的边界

- 当前是单节点进程监督。多节点 DDP、Ray 或远程调度任务需要额外的集群任务 ID、所有节点结束确认及租约协调；本机 shell 退出不能证明远端任务已结束，不能直接套用当前的自动恢复判断。
- MIG 分区、MPS 共享、非 NVIDIA GPU 不在当前心跳支持范围。分区指标或设备映射不能确认时暂停负载，不扩展到整张物理卡；NVIDIA 也说明部分 MIG 利用率指标不可用。[nvidia-smi 文档](https://docs.nvidia.com/deploy/nvidia-smi/)
- 绕过 Mochi 启动的外部任务只能从其 GPU 进程出现后识别。完整的 CPU 准备、训练和保存保护需要通过 Mochi 提交。
- 负载启动和退出仍取决于 CUDA 初始化、驱动响应和操作系统调度；驱动卡死时保留故障状态，不承诺自动修复或固定切换时延。
- 真实任务优先，空闲阶段默认目标 90%；任意硬件的达标率和全程平均利用率都需要实际采样。

## 本轮验证

无多卡 GPU 实机。自动测试使用真实的 1 / 2 / 4 / 8 个 CPU 子进程和模拟 GPU 指标，覆盖顺序变化、非连续设备子集、独立反馈、单卡故障/消失/显存压力、启动延迟、拒绝 TERM、宿主机 PID 命名空间、外部进程存活、指标 `N/A` 和跨主机遗留锁。没有把模拟结果当作 CUDA/NCCL 实测。

3.5.0 的单卡 H100 结果作为历史证据保留；本轮旧 SSH 入口拒绝连接，未在远端替换服务。具体测试计数及复现方式见 [测试记录](TESTING.md)。
